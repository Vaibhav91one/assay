---
title: Configuring credentials
description: The four credentials Assay can use, what each one buys, and what happens without it.
---

Assay reads its credentials from the environment when it starts. Copy
`.env.example` to `.env`, put in what you want, and restart. **What you leave
out stays off** — none of these is required to boot, and the sign-in screen
reports each one by presence only.

<Callout type="warn" title="Presence only, everywhere">
  Nothing in Assay renders, logs or echoes a credential's value — not whole, not
  masked, not the last four characters. The sign-in panel and the Settings panel
  both report a boolean and a route name and have nowhere to put a value. If you
  ever see one of these keys on a screen, that is a bug worth reporting.
</Callout>

A process keeps the environment it started with. If you export a variable in a
terminal after Assay is already running, that Assay cannot see it and never
will — restart it.

## Model access

**What it buys:** field discovery and second-opinion checks.

**What happens without it:** Assay runs. This is the one thing about the model
path worth saying loudest, and it is true rather than reassuring:

> Assay runs with no model. A model only ever proposes; the gate decides.

The rule from `docs/AI-AND-AGENTS.md` §1 is **the model proposes, it never
decides**. An LLM may suggest which element a field moved to; everything it
suggests goes through the same `tau` and `delta` gate as everything else, with
no special path, no override and no confidence multiplier. And the model returns
**element references, never values** — Assay reads the node's text out of the
DOM itself, so no string a model produced ever reaches your data. That closes
prompt injection by construction rather than by filtering. Without a model you
lose candidate suggestions and second opinions, and you lose nothing that
decides anything.

### Three routes, and which one you want

There are three ways to satisfy the model path, and any one of them is enough.

<Tabs items={['API key', 'claude setup-token', 'An existing Claude Code login']}>

<Tab value="API key">

Set `ANTHROPIC_API_KEY` to a key from the Claude Console.

```bash
ANTHROPIC_API_KEY=
```

**This is the route a shared deployment must use.** See the box below.

</Tab>

<Tab value="claude setup-token">

On your own machine, with a Claude subscription, run Anthropic's own CLI:

```bash
claude setup-token
```

It opens your browser to authorise and then prints a token. Put that in your
environment as `CLAUDE_CODE_OAUTH_TOKEN` and restart Assay.

```bash
CLAUDE_CODE_OAUTH_TOKEN=
```

Assay implements no login of its own: no client id, no redirect, no token
exchange, nothing stored. This is Anthropic's CLI authenticating your machine,
and Assay then reads the resulting variable exactly as it reads the API key.

</Tab>

<Tab value="An existing Claude Code login">

**If you are already signed in to Claude Code on this machine, there is nothing
to set and nothing to restart.**

The Agent SDK falls back to the CLI's own credential store on its own. Assay
asks `claude auth status` whether that store has a login and never opens it.
When the answer is yes, the model path is satisfied with no variable at all —
which is why the sign-in screen and the Settings screen both say *Connected
through Claude Code on this machine* rather than naming a variable.

Two things follow from that. The probe costs a few seconds the first time
(measured at 2.9–4.8s cold), so its answer is cached for the life of the
process. And **Check again** in Settings is the only thing that drops that
cache — it is there because a panel that says "no model" has to offer a way to
be wrong about that.

</Tab>

</Tabs>

<Callout type="error" title="A shared deployment must use an API key">
  This is not a preference. The Claude Agent SDK overview states:

  > Unless previously approved, Anthropic does not allow third party developers
  > to offer claude.ai login or rate limits for their products, including agents
  > built on the Claude Agent SDK. Use the API key authentication methods
  > described in the Quickstart instead.

  A single operator authenticating their own machine with Anthropic's own tool
  is not Assay offering anyone a login. A deployment other people sign in to
  takes the API key. `docs/STACK.md` §0 records this as an owner decision:
  authentication is **BYOK**.
</Callout>

### What the sign-in screen reports

The panel reports **whether the capability is satisfied**, not whether a
particular variable is set — because those are different questions and only the
first one is the one you care about. A machine whose Claude Code CLI is signed
in has a working model path and two empty variables, and a panel that reported
the variables would send you to fix something that is not broken.

So the model row is Connected when any of the three routes answers, and it names
the one that did.

## Bright Data

Bright Data is **two separate things**, pointing in opposite directions, and
setting one does not configure the other. Settings shows them as two rows for
that reason.

| | Where it lives | What it buys |
|---|---|---|
| **API token** | `BRIGHTDATA_API_TOKEN`, in the environment | **Assay calls Bright Data.** Read by `tools/bd-heal.ts` and `tools/bd-status.sh`. |
| **Delivery webhook** | a secret in `data/connectors.json` | **Bright Data calls Assay** — it POSTs a scraped page to `/api/v1/connectors/brightdata/delivery/:target`. |

**What happens without either:** Assay still runs against anything a plain fetch
can reach, and against the committed corpus — the benchmark, the replay and the
test suite are all offline and need no token at all. Nothing in Assay *fetches a
page* through Bright Data; the connector that does that is
[Firecrawl](#firecrawl), below.

### The API token

```bash
BRIGHTDATA_API_TOKEN=
```

Your own token. **Assay never ships one.** One name, everywhere: `.env.example`
declares it, the sign-in panel reports it, and `tools/bd-heal.ts` and
`tools/bd-status.sh` read it and error out by that name if it is absent.

<Callout type="warn" title="Authenticating is not fetching">
  A token can be entirely valid and still fetch nothing. Bright Data checks the
  token *and* a zone on the account, and reports them separately:

```bash
curl -sH "Authorization: Bearer $BRIGHTDATA_API_TOKEN" https://api.brightdata.com/status
```

  On the account this build was developed against, that returns (2026-08-23):

```json
{"status":"active","customer":"hl_03fc6be2","can_make_requests":false,"auth_fail_reason":"zone_not_found"}
```

  **Active, authenticated, and unable to make a request** — because no zone
  exists. That is a real third state between "no token" and "working", and it is
  why the Settings row says the token is *set* rather than saying Bright Data is
  *connected*. Assay does not run this check on page render: it would send your
  token to a third party every time you opened Settings, and the answer would be
  stale the moment it was painted. Presence is a fact Assay owns; reachability
  is Bright Data's, and it changes without Assay hearing about it.
</Callout>

### The delivery webhook

Minted by Assay and pasted into Bright Data's webhook configuration — Bright
Data publishes no signature scheme, so authenticity rests on a bearer you
supply and it echoes back.

```bash
npx tsx tools/cli/connectors.ts set brightdata
```

It prints the secret **once**. Set it on the job as `auth_header=Bearer …`.

<Callout type="warn" title="This one cannot be finished on localhost">
  Bright Data POSTs to your instance from its own network, so the URL you give
  it has to be publicly reachable. `http://localhost:3000` is not, and neither
  is anything on your LAN. Mint the secret locally by all means — the delivery
  will not arrive until Assay is somewhere Bright Data can reach.
</Callout>

`src/runner.ts` takes `fetch` as a parameter, so the local worker and the Bright
Data webhook path run identical detection and gating. There is no second code
path with weaker checks on it.

### The finding that came out of using it

Worth reading before you rely on any collector's own success reporting. A
Scraper Studio collector (`c_mt1nrjboski90goqc`, Code worker) scrapes IKEA's
product-recall listing and its detail pages. It returned **60 records**, and
Bright Data reported the run as **100% successful, 0 failed crawls**.

But three fields the approved schema promises — `recall_title`, `recall_url` and
`date_published` — are **absent from all 60 records**, and `product_name` and
`hazard` appear in one row each.

A green run and empty columns. That is the same failure this whole project is
about, arriving unprompted from production. `npm run audit` reads the raw API
response off disk and reports the gap;
`results/j_mt1q17uoq8rkcxd8a.ndjson` is Bright Data's unmodified response.

## Firecrawl

**What it buys:** reads a page that refuses a direct request.

**What happens without it:** nothing changes. Assay reads pages exactly as it
always has. This is the connector that fetches a page a plain request cannot
get — it is the only one, and it is not Bright Data.

```bash
FIRECRAWL_API_KEY=
```

Your own key. **Assay never ships one.**

Two things have to be true before a single request goes to Firecrawl, and they
are separate on purpose:

1. `firecrawl` is in the sources file — `data/skills.json`, or wherever
   `ASSAY_SKILLS` points. The whole file is one line:

   ```bash
   echo '{"enabled":["firecrawl"]}' > data/skills.json
   ```

2. `FIRECRAWL_API_KEY` is present in the environment of the process making the
   request — the worker, which is a second process beside Next, so export it
   where the worker starts.

A key sitting in a shell is not consent to route your traffic through a third
party, which is why the second does not imply the first.

Enabling it does not route your traffic through Firecrawl. Assay tries a direct
request first and only falls back when that request is refused, which is the
same rule Bright Data has always followed here. A page a plain fetch can read
never reaches Firecrawl and never costs you a credit.

What comes back is `data.rawHtml` — the unmodified HTML the site served, not
markdown. Assay resolves fields against the DOM, so a converted document would
mean writing contracts against something the site never sent. The bytes then go
through `src/runner.ts`'s `fetchPage` parameter, which is the same seam a Bright
Data delivery and a local fetch use, so the gate, the thresholds and the
published wrong-value rate cover a Firecrawl-fetched page unchanged. There is no
second extraction path.

A 200 carrying no `rawHtml` is treated as a failure, not as an empty page. The
distinction matters: an empty page would read downstream as *the field
disappeared*, which is exactly the green-run-empty-column failure recorded under
Bright Data above.

## Email delivery

**What it buys:** sends the break alert and the digest.

**What happens without it:** alerts are not sent. Nothing else changes —
detection, healing, gating and quarantine all run and are all recorded, and the
decisions are in the app and in `results/`. You lose the push, not the signal.

```bash
ASSAY_RESEND_KEY=
ASSAY_MAIL_FROM=
ASSAY_MAIL_TO=
```

Your own Resend key and your own verified sending domain. `ASSAY_MAIL_FROM`
is the address alerts come from; Resend will not send from a domain you have not
verified with them, so both are needed for mail to leave. `ASSAY_MAIL_TO` is the
default recipient when a delivery does not name its own.

The key carries the `ASSAY_` prefix because it sits with `ASSAY_MAIL_FROM` and
`ASSAY_MAIL_TO` and is read by the same function: `src/notify.ts` reads all
three, `docker-compose.yml` passes all three to the worker, and the sign-in
panel reports the first of them.

Delivery is optional, and deliberately so — the compose file's own comment
records the rule as *"with no key the worker records the break as undelivered
and carries on. An unset key must never stop a run."*

If you are alerting to something other than email, the worker also reads
`ASSAY_WEBHOOK_URL` and `ASSAY_WEBHOOK_SECRET`.

Alerts are push by design. From `docs/FEATURES.md` §5: *alerts are push, never a
page you must remember to visit* — and a notification bell is on the
anti-features list for the same reason.

## The variables Assay does not ask you for here

`.env.example` carries the rest, and none of them is a credential this page can
help with:

| Variable | What it is |
|---|---|
| `DATABASE_URL` | Where Postgres is. Covered in [Getting started](/docs/self-host). |
| `ASSAY_CAPTURES` | The captures directory. Covered in [Architecture](/docs/architecture). |
| `ASSAY_MODEL` / `ASSAY_CHAT_MODEL` | Model ids for the healer and for the in-app agent. Blank means the default. |
| `ASSAY_CONNECTORS` / `ASSAY_CONNECTOR_HOSTS` | Where the connector config lives, and the hosts a connector may reach. |
| `ASSAY_SKILLS` | Where the page-sources file lives. See [Firecrawl](#firecrawl). |
| `AUTH_MODE` | `none` for single-operator self-host (the default), `clerk` for a hosted instance. |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` / `CLERK_SECRET_KEY` / `NEXT_PUBLIC_CLERK_SIGN_IN_URL` | Only read when `AUTH_MODE=clerk`, and read by `@clerk/nextjs` rather than by Assay — so they are Clerk's own names. The publishable key is read in the browser and must carry the `NEXT_PUBLIC_` prefix or Next never inlines it; without the sign-in URL, `auth.protect()` redirects to Clerk's hosted Account Portal instead of Assay's own screen. |

Self-hosting is single-operator: `AUTH_MODE` defaults to `none`, so a clone boots
with no account, no signup and no keys. `@clerk/nextjs` is deliberately **not** a
dependency here, so a self-hoster never downloads an auth SDK they will never
load.

<Callout type="warn" title="Self-hosted mode authenticates nobody">
  With `AUTH_MODE=none` there is no sign-in and no account, so **anyone who can
  reach the port can use the instance** — read every run, resolve held cells,
  add and pause scrapers. That is the intended shape for a single operator, and
  it assumes a network boundary you provide: a private network, a VPN, or a
  reverse proxy that authenticates. Do not put it on a public address as it
  ships.
</Callout>
